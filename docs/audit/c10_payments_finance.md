# Cluster 10 Audit — Domains 64-72: Payments, Disputes, Refunds, Expenses, Revenue, Profit, ROI

Summary: Domains 64-68 (Payments/Partial Payments/Failed Payments/Disputes/Refunds) sit on a
genuinely honest, well-documented **sandbox-only** payment layer (`PaymentProvider.SANDBOX`
is the only value ever produced by `payment_service.py`/`sale_order_service.py`; the stack
table in `README.md` and `docs/LICENSE_REGISTER.md` confirm free/open-source only, no real
gateway dependency was ever added) with real dispute/refund state machines, admin-only
resolution, and solid test coverage for the *happy* paths — but with three concrete gaps
that are not merely "future scope": (1) there is **no partial-payment concept anywhere** in
the `Payment` model/schema (amount is always the full order/sale value), (2) a **failed
payment cannot be retried** through the existing API — `payment_service.initiate_payment()`
re-applies the `PAYMENT_PENDING` transition, which the transition map
(`app/models/order.py:54`) does not allow from a `PAYMENT_PENDING` order, so retrying
produces a 409, not a new payment attempt, and (3) **no farmer-facing `Notification` row is
ever created for a payment success/failure or dispute event** — only `AuditLogger` entries
exist, which are an internal audit trail, not a notification. Domains 69-72 (Expenses,
Revenue, Profit, ROI — Phases 29-33) are, as flagged, the strongest cluster in the whole
system: a real manual+sale-linked+invoice-linked ledger, genuinely-run local Tesseract OCR
with a structurally-enforced "OCR never auto-posts to the ledger" rule, honest
`Literal[None]`-typed estimated-revenue/ROI fields where no real data source exists (rather
than fabricated numbers), and 74/74 targeted tests passing in this session
(`test_ledger.py`, `test_invoices.py`, `test_crop_financials.py`, `test_profit_forecast.py`,
`test_orders.py`). The one clear architectural gap in this otherwise-excellent cluster is
that every financial computation is scoped to a single `crop_cycle_id` — there is no
Plot-level, Farm-level, or Season-level P&L aggregation anywhere, and no cost/acre,
revenue/acre, or profit/acre computation despite `Plot.area_value`/`area_sqm` existing and
being fully available to join against.
