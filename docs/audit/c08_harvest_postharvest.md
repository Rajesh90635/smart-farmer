# Harvest / Post-Harvest Audit — Domains 47-55

Summary: The codebase implements one real, well-tested lifecycle — `HarvestRecord` (`backend/app/models/harvest_record.py`) with an 8-value `HarvestStatus` enum (`planned→approaching→ready→harvested→listed→partially_sold/sold→cancelled`) feeding into `HarvestListing`→`BuyerOffer`→`SaleOrder` (Prompt 10 marketplace) — and every scenario in Domains 47-52 maps onto facets of that one lifecycle plus its free-text `quality_grade`/`unit` fields and the `profit_forecast_service`'s reuse of `estimated_quantity`/`actual_quantity` as "yield". Farmer-confirmation-only status advancement (never automatic) is explicitly designed and verified by test. Two real, disclosed gaps run through several rows: (1) no code path anywhere ever sets `HarvestStatus.HARVESTED`/`PARTIALLY_SOLD` or writes `HarvestRecord.actual_quantity` — `docs/HARVEST_MANAGEMENT.md:20-26` discloses this as an intentional, unwired gap; (2) `harvest_service.confirm_ready()` has no status guard, so calling it again to "correct" a quantity silently regresses `LISTED`/`HARVESTED` records back to `READY` — a real bug. Domains 53 (Storage), 54 (Cold Storage) and 55 (Transport) are almost entirely unimplemented: the only artifacts found across the whole backend are a `CollectionOption.THIRD_PARTY_LOGISTICS` label on `HarvestListing.delivery_option`, a `LedgerCategory.TRANSPORT` bookkeeping category (farmer's own manual expense tagging, not a booking), and a vocabulary-only `Role.TRANSPORTER`/`Role.LAB` with zero seeded rows, zero endpoints, and zero models — confirmed by exhaustive grep, not assumed. All 12 tests in `test_harvest.py`, all 31 in `test_weather_actions.py`+`test_profit_forecast.py` pass (`cd backend; pytest tests/test_harvest.py tests/test_weather_actions.py tests/test_profit_forecast.py -q` → `12 passed` / `31 passed`).
