# Audit: Domains 21-26 — Seeds, Fertilizer, Crop Protection, Input Inventory, Input Purchase, Input Verification

Summary: This project has **no farmer-facing input-inventory system at all** (Domain 24 is
almost entirely MISSING — there is no model tracking what a farmer owns, how much of it
remains, or when they used it on their farm). What it does have is a real, well-tested
**dealer marketplace** (`Product` master catalog + `DealerProduct` listings + `Order`/
`OrderItem` checkout + `ReferencePrice`/price-comparison + a single-factor "Scam Shield"
price-anomaly check), documented in `docs/PRODUCT_CATALOG.md`, `docs/PRICE_TRANSPARENCY.md`,
`docs/SCAM_SHIELD.md`, `docs/ORDER_WORKFLOW.md`, `docs/PRODUCT_SAFETY.md`, and
`docs/PROMPT9_ASSUMPTIONS_RISKS.md`, which honestly cover Domains 21-23 and 25 as "buy an
approved agricultural input from a verified dealer, at a server-calculated price, with an
informational (never blocking) price-fairness check." Seeds (Domain 21) are literally
`Product` rows with `category=SEED` reusing the identical catalog/order code
(`docs/SEED_MARKETPLACE.md`) — there is no seed-specific requirement calculator or variety
field. Domain 26 (Input Verification) is strong on seller/product/price/expiry transparency
and has a genuinely working, tested OCR receipt-capture feature (`invoice_service.py`,
`tesseract_ocr_provider.py`, `test_invoices.py`) with an absolute farmer-confirmation gate
before anything reaches a financial ledger, but has **no authenticity/counterfeit-detection
mechanism** — this is explicitly disclosed as a known gap in
`docs/PROMPT9_ASSUMPTIONS_RISKS.md` ("Product has no QR/barcode verification capability").
Order-status push notifications (`ORDER_ALERT`) are explicitly, deliberately not built
(`docs/NOTIFICATION_ARCHITECTURE.md:49-51`), so all order/inventory-adjacent facts in this
audit are pull-only (farmer must open the app and check), never push-notified.
