# C02 — Lifecycle Edge Cases Audit (Domains 9, 10, 11, 12, 13, 99)

This audit covers Task Automation, Crop Failure, Re-Sowing, Intercropping, Perennial Crops, and Special Crop Scenarios against the actual code in `backend/app` and `mobile/lib`. The headline finding is structural: `CropCycle` (backend/app/models/crop_cycle.py) has exactly one non-terminal exit for anything going wrong — a generic `CANCELLED` status reachable from any active state with no reason/category field anywhere in the model, schema, service, or Flutter UI — so every failure-cause facet (disease/pest/drought/flood/weather/other), failure confirmation, recovery recommendation, and re-sowing linkage is absent as a *named* feature. Similarly, `Task` (backend/app/models/task.py) is deliberately farmer-created-only per an explicit anti-fabrication decision recorded in `PROJECT_STATUS.md`, so automatic creation, reminders, snoozing, rescheduling, recurrence, dependencies, and skip/reject/fail states are all absent by design or by gap. Intercropping and perennial-specific handling are not deliberately built either way — the plot/crop-cycle model would *accidentally* tolerate concurrent cycles on one plot (no exclusivity constraint), and per-cycle foreign-key scoping on tasks/harvests/ledger entries means any concurrent cycles would incidentally get separated data — but nothing is designed, tested, or exposed in the UI as "intercropping" or "perennial mode." The one genuinely strong, tested area in this whole audit is multi-harvest support (`HarvestRecord`, one row per harvest event) and sequential crop-cycle history preservation, both real and verified by name.
