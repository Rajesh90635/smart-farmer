# Database

PostgreSQL, accessed via SQLAlchemy, schema evolved via Alembic. **Every**
schema change is a migration — no direct manual table creation, per the
development rules.

## Connection

`app/db/session.py` builds the engine from `DATABASE_URL` (env var), with
connection pooling (`pool_size`, `max_overflow` from settings) and
`pool_pre_ping=True` so a dropped connection is detected before it causes a
request failure rather than during one.

## A real bug found and fixed during this phase

The initial autogenerated migration stored Postgres enum labels as the
Python enum **member names** (`ACTIVE`, `INACTIVE`, `SUSPENDED`) rather
than their intended lowercase **values** (`active`, `inactive`,
`suspended`) — SQLAlchemy's `Enum` type defaults to member names unless
told otherwise. Fixed by adding `values_callable=lambda e: [x.value for x
in e]` to every `SAEnum(...)` column definition
(`app/models/user.py`, `app/models/consent_record.py`) before the
migration was applied — verified by inspecting the actual DB enum labels
after migration, not just by reading the code.

## A second real bug found and fixed (Farm/Plot/Crop phase)

Autogenerated `downgrade()` functions drop tables but do **not** drop the
Postgres `ENUM` types those tables' columns used — found by actually
running `alembic downgrade -1` then `alembic upgrade head` and hitting
`type "area_unit" already exists`. Fixed by adding explicit
`sa.Enum(name='...').drop(bind, checkfirst=True)` calls to the downgrade
function, in reverse dependency order, for every custom enum the migration
introduces. Verified by running the full upgrade → downgrade → upgrade
cycle successfully afterward. This is a known, easy-to-miss Alembic/
Postgres interaction — check for it in every future migration that
introduces a new enum type.

## A real bug found and fixed (Crop Photo phase, applied proactively since)

See docs/IMAGE_STORAGE.md for the storage-key mismatch bug found in the

## A real bug found and fixed (AI Disease Detection phase)

A seed-data `INSERT ... UNION ALL` mixed JSONB string literals with bare
`NULL` values across branches — Postgres couldn't infer a consistent type
across the `UNION`, failing with `column "local_names" is of type jsonb
but expression is of type text`. Fixed by adding explicit `::jsonb` casts
to every literal and `NULL` in the affected `UNION ALL` (see the
`4cac6105f1a7` migration). A reminder that `UNION`-based seed-data inserts
need every branch's literal types made explicit, not just the column's
declared type.

## A third proactive enum-drop fix (Weather + Notifications phase)

Same fix from prior phases applied proactively to the weather/notification
migration before ever running it — verified via a full
upgrade→downgrade→upgrade cycle plus `alembic check` (zero drift), on the
first attempt this time. No new bug this phase.

## Migration workflow

```powershell
# After changing/adding a model in app/models/*.py:
cd backend
alembic revision --autogenerate -m "short description of the change"

# Review the generated file in alembic/versions/ before applying -
# autogenerate is a strong starting point, not a guarantee of correctness
# (it can miss some column-type changes, for example).

alembic upgrade head      # apply
alembic downgrade -1      # roll back one step, if needed
alembic current           # show current revision
alembic history           # show full migration history
```

**Important:** any new model module must be imported in `alembic/env.py`
(alongside `from app.models import audit_log`) or autogenerate will not see
it — this is a common Alembic footgun, documented here so it isn't
rediscovered the hard way.

## A real bug found and fixed (Professional Network phase) — role-seed downgrade

Same class of bug as the enum-drop issue, but for a data seed instead of a
schema object: the `INSERT INTO roles ('trader')` in `upgrade()` had no
corresponding removal in `downgrade()`, so a downgrade→upgrade cycle
failed with a duplicate-key error on `trader`. Found by actually running
the cycle. Fixed by adding `DELETE FROM roles WHERE code = 'trader'` to
`downgrade()`, then re-verified the full cycle twice — clean both times.
A reminder that data-seed migrations need the same symmetry discipline as
schema-object migrations, not just enum types.

## A real bug found and fixed (Marketplace phase) — schema/response field mismatch

`PaymentInitiateResponse` was defined with a field named `payment_id`,
but the `Payment` model's primary key column is `id` (matching every
other model in this codebase). This caused a `pydantic.ValidationError`
on every single call to the payment-initiation endpoint, cascading into 5
failing tests across the full order lifecycle, payment-failure, dealer
rejection, and dispute/refund test suites. Found by actually running the
tests (not by inspection), fixed with an explicit field mapping in the
schema, and confirmed all 5 cascading failures cleared afterward.

## A second real bug found and fixed — checkout skipping a state-machine step

`order_service.checkout()` originally jumped directly from `DRAFT` to
`CONFIRMED`, silently bypassing the `PENDING_CONFIRMATION` intermediate
state the transition map itself required. Found while consolidating
duplicated transition-validation logic across three services into one
shared module — the inconsistency became visible once there was a single
source of truth to check against. Fixed by making checkout explicitly
pass through both transitions in sequence.

## A third real gap found and fixed — checkout not re-verifying product safety status

`order_service.checkout()` originally only checked the `DealerProduct`
listing's own `is_available` flag and stock — it never re-checked the
underlying `Product.status` (a product suspended/recalled after being
listed would still be purchasable) or the listing's own `expiry_date`.
Found while writing docs/PRODUCT_SAFETY.md and cross-checking its claims
against the actual code — the doc initially claimed a protection that
didn't exist. Fixed by adding both checks to checkout, and added two new
tests (`test_checkout_fails_if_product_suspended_after_listing_created`,
`test_checkout_fails_on_expired_listing`) confirming the fix, both
passing.

## A real migration bug found and fixed — twice, in the same spot (Harvest Marketplace phase)

Autogenerate produced `op.drop_constraint(None, ...)` calls for the
newly-nullable `order_id` columns on `payments`/`deliveries` — Alembic
cannot compile an unnamed constraint drop. Found the real constraint
names directly from Postgres's system catalog
(`pg_constraint`) and fixed the downgrade. On the next verification pass,
found a SECOND, redundant duplicate drop statement for the same
`payments` foreign key that autogenerate had also emitted, which was
removed. Only after both fixes did a full upgrade→downgrade→upgrade cycle
succeed — **verified twice** in a row, zero schema drift.

## A real concurrency guarantee, verified with an actual test (not just designed)

`harvest_repository.get_listing_for_update()` uses `SELECT ... FOR UPDATE`
to lock a `HarvestListing` row before checking/decrementing
`quantity_available` during offer acceptance. This was verified with a
genuine multi-threaded test (two Python threads calling the accept
endpoint simultaneously against a listing that can't satisfy both) — run
5 times consecutively to rule out a lucky non-race rather than a real
database guarantee. All 5 runs produced the identical correct outcome:
exactly one success, one correctly-rejected failure, never an oversell.
